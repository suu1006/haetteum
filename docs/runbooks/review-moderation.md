# 후기 신고와 작성자 차단

## 배포

`20260914020000_review_moderation` 마이그레이션을 API 배포 전에 적용한다.

```sh
pnpm --filter @haetteum/api db:deploy
```

`review_reports`, `user_blocks` 테이블만 추가하는 마이그레이션이다. 기존 후기는 변경하지 않는다. 이번 구현 검증은 별도 임시 PostgreSQL에서 수행하며 실제 운영 DB에는 적용하지 않는다.

## 사용자 동작

- 장소의 해뜸 후기 메뉴에서 로그인 후 신고하거나 작성자를 차단한다. 자신의 후기에는 메뉴가 나타나지 않으며 API도 본인 신고·차단을 거절한다.
- 신고 사유: 광고·스팸, 욕설·괴롭힘, 부적절한 내용, 개인정보 노출, 기타. 상세 내용은 선택 입력이며 최대 1,000자다.
- 같은 사용자의 같은 후기 신고는 1회만 접수된다. 접수 상태는 `PENDING`이다. 신고자의 정보는 작성자에게 공개하지 않는다.
- 신고만으로 후기를 자동 삭제하거나 전체 공개 목록에서 숨기지 않는다.
- 차단은 로그인한 본인의 후기 목록 및 해당 목록의 평점 집계에만 적용한다. 다른 사용자와 비로그인 열람에는 영향이 없다. 여러 기기에서도 같은 계정으로 로그인하면 유지된다.
- 마이페이지 → 차단한 사용자에서 해제한다. 차단된 작성자에게 알림을 보내지 않는다.
- 후기 조회는 쿠키별로 달라지므로 `Cache-Control: private, no-store`를 유지한다. 프록시/CDN에서도 강제 공개 캐싱을 하지 않는다.

## 신고 검토

회원탈퇴 시에는 작성자에 대한 신고 스냅샷과 본인이 접수한 신고도 삭제한다. 일반 후기 삭제의 증거 보존과 구분한다. [회원탈퇴 운영 기준](account-deletion.md)을 따른다.

이번 범위에는 운영자 관리 화면·알림·제재 자동화가 포함되지 않는다. 담당자는 권한이 제한된 DB 도구에서 접수 내용을 확인한다.

```sql
SELECT id, review_id, review_id_snapshot, author_id_snapshot,
       reason, details, title_snapshot, content_snapshot, created_at
FROM review_reports
WHERE status = 'PENDING'
ORDER BY created_at;
```

신고 당시 제목·본문과 원래 후기·작성자 ID를 별도로 저장한다. 원본 후기가 삭제되어 `review_id`가 NULL이 되어도 해당 기록은 남는다. 사진 파일의 복사 보관은 하지 않는다. 운영자는 스냅샷과 현재 후기를 함께 확인하고 판단한다. 실제 제재·처리 상태 관리 및 보존·삭제 기간 정책은 운영 절차를 마련해야 한다.

## 검증

- API E2E: 실제 세션/Origin 검증, 잘못된 입력, 본인 신고·차단 방지, 동시 중복 신고, 반복 차단, 차단 사용자별 조회·해제 권한, 삭제 후 신고 기록 보존.
- 웹: 신고 접수, 차단 확인, 성공 후 숨김, 실패 시 유지, 차단 해제, 비로그인 안내와 본인 메뉴 숨김, 서버 쿠키 전달.
