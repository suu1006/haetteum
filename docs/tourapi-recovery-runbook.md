# TourAPI 실패 복구 운영 절차

일일 1,000회는 데이터 건수가 아니라 HTTP 요청 횟수다. 관광지700회·축제300회 안에서 목록과 상세를 수집한다. 정상 상세는 원본 버전이 바뀌지 않으면 다시 받지 않는다.

## 저장 실패 복구

1. 먼저 현재 원본 버전의 실패·격리를 안전하게 조회한다. 아래 명령은 읽기 전용이며 HTTP를 보내지 않는다. 기본 20개, 최대 100개이고 `--ids`로 최대 100개의 숫자 ID를 지정할 수 있다. 원문은 `tour_api_captures`에 남고 Notion/로그에 출력하지 않는다.

```sh
pnpm --filter @haetteum/api tourism:inspect -- --job=tourism --limit=20
pnpm --filter @haetteum/api tourism:inspect -- --job=festival --limit=20
```

출력의 `sourceVersion`, `stage`, `code`, `attemptCount`, `nextAttemptAt`과 `state`를 확인한다. 만료 전 대기와 3회 실패 후 격리는 이번 실행의 신규 실패 수와 다르다.
2. 파서 또는 데이터 저장 문제를 수정한 다음, 저장된 응답만 사용해 소수 항목을 재처리한다.

```sh
pnpm --filter @haetteum/api tourism:replay -- --job=tourism --ids=2704412 --limit=1
pnpm --filter @haetteum/api tourism:replay -- --job=festival --ids=123456 --limit=1
```

위 ID는 형식 예시이며 실제 실패 ID로 바꾼다. 기본 모드는 API를 호출하지 않는다. 응답이 부족하면 보류한다. 대상 버전이 바뀌거나 격리 상태가 바뀌면 선택을 다시 확인하며 새 버전을 임의 처리하지 않는다.

3. 응답 자체를 받지 못한 단계가 있고 호출 예산이 남아 있을 때만 누락된 응답을 가져온다.

```sh
pnpm --filter @haetteum/api tourism:replay -- --job=tourism --ids=2704412 --limit=1 --fetch-missing --max-requests=4
```

`max-requests`에는 추가 재시도도 포함된다. 요청 수가 부족하면 보류하며 전역·작업별·복구 예산을 우회하지 않는다. 인증/일일한도 오류는 반복 호출로 해결하지 않는다.

4. 3회 실패한 격리 항목은 원인을 수정한 뒤 명시적으로 선택해 다시 넣는다.

```sh
pnpm --filter @haetteum/api tourism:replay -- --job=tourism --ids=2704412 --limit=1 --requeue
```

기존 정상 데이터, 장소ID, 즐겨찾기와 리뷰 관계는 유지한다. 최종 저장 직후 프로세스가 중단돼도 다음 실행에서 저장된 버전을 확인해 실패 이력을 정리한다.

## 주의할 복구 범위

- 배포 이전 실패건은 당시 응답이 보관돼 있지 않으므로 이 기능만으로 과거 응답을 되살릴 수 없다. 다음 배치의 필요한 호출부터 보관한다.
- 목록은 같은 날짜·같은 조회 조건의 미완료 응답만 복구한다. 복구 후 새 목록 확인까지 성공해야 체크포인트 또는 누락 항목 비노출 처리를 진행한다.
- 원본 버전이 달라지면 이전 상세 응답을 새 버전에 쓰지 않는다.
- 보관 DB 자체 장애는 수집을 중단한다. DB 복구 후 재개하며 응답을 영구 보관하기 전에 프로세스가 종료된 요청은 다시 필요할 수 있다.
- 미해결 응답은 자동 삭제하지 않는다. 완료 응답의 보관 정리는 문서화된 제한 수로 별도 수행한다.

## 보존과 배포 후 검증

완료 응답만 `TourApiRecoveryRepository.cleanup(before, limit)`으로 정리할 수 있다. 완료 시각 기준 예를 들어 30일 이전, 한 번에 100개처럼 작은 범위를 사용하며 함수의 최대 한도는 1,000개다. 정리 CLI와 자동 정리 스케줄은 제공하지 않는다. 미완료·격리 증거는 자동 삭제하지 않고 운영 판단 전까지 보존한다. 새 원본 버전은 새 작업이므로 과거 실패는 현재 복구 슬롯과 조회 결과에 포함되지 않는다.

수동 명령은 스케줄러를 끄며 replay는 정기 배치와 같은 advisory lock을 사용한다. 조회는 데이터를 변경하지 않으므로 잠금을 요구하지 않고, 조회 직후 상태가 바뀔 수 있다. replay 실행 직전에 버전과 상태를 다시 검증한다. `--fetch-missing`의 요청 상한은 기존 공용·작업별·복구 예산과 cooldown/deadline 안에서만 동작한다. 보류 종료 코드는 2, 실패는 1, 성공은 0이다. inspect 성공은 0이며 조회 실패는 1이다.

Notion 외부 속성 변경 없이 기존 성공/실패/보류와 숫자 실패 건수를 사용한다. 일부 상세가 실패해도 성공 상세는 유지한다. `locallyReplayedCount`는 이번 실행에 저장 응답만으로 성공한 항목 수이며 혼합 HTTP 성공은 제외한다. 상세 잔여에는 대기·격리가 포함된다. 상세 실패가 하나라도 있으면 보류보다 실패 상태를 우선한다.

과거 103건의 정확한 실패 원인은 아직 입증되지 않았다. 당시 캡처가 없다면 이 명령만으로 원문을 복구할 수 없다. 이후 캡처를 근거로 판단하고 검증을 위해 전체 운영 배치를 실행하지 않는다.
