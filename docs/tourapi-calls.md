# TourAPI 호출 구조 및 규칙

최종 구조 확정일: 2026-09-12

이 문서는 TourAPI 관련 구현과 코드 리뷰에서 반드시 확인해야 하는 호출 정책이다. 아래 구조를 기준으로 호출 코드를 전환했다. 실행 환경에 새 마이그레이션을 적용하고 초기 상세 수집을 완료해야 저장된 상세 데이터가 제공된다. 기존 설계 문서나 현재 구현과 충돌하면 이 문서의 호출 정책을 기준으로 변경한다.

## 최종 구조

```text
TourAPI
  │ 정해진 배치에서만 호출 (HTTP 요청은 TourApiClient 담당)
  ▼
tourism-sync
  ├─ 변경 목록 수집
  ├─ 신규 / 수정 / 삭제·비노출 판별
  ├─ 필요한 상세정보만 추가 호출
  └─ PostgreSQL upsert 및 삭제·비노출 상태 반영
           │
           ▼
      PostgreSQL
       ├─ 랭킹
       ├─ 검색
       └─ AI 코스
          DB 조회
```

## 필수 호출 경계

**TourAPI 직접 호출은 `TourApiClient` 외에는 금지한다.**

- TourAPI HTTP 요청, 인증 파라미터 구성, 재시도, 속도 제한 및 일일 호출 한도 처리는 `TourApiClient`를 공통 진입점으로 사용한다. 다른 파일에서 `fetch`, Axios 또는 별도 HTTP 클라이언트로 TourAPI를 호출하지 않는다.
- `tourism-sync`는 정해진 수집 배치에서 TourAPI 포트를 통해 `TourApiClient`를 사용한다. 배치 서비스가 직접 HTTP 요청을 구현하는 것은 금지한다.
- 랭킹·검색·AI 코스를 비롯한 사용자 요청 처리 경로는 저장된 TourAPI 데이터를 PostgreSQL에서 조회한다. `TourApiClient`나 TourAPI 포트를 간접 호출하는 방식으로도 외부 수집을 실행하지 않는다.
- 축제 상세, 주간 추천, 랭킹 매칭·이미지 보강 등에도 같은 경계를 적용한다. 필요한 외부 데이터 수집은 `tourism-sync` 수집 단계에 모으고 각 기능은 저장된 결과를 사용한다.
- DB에 데이터가 없거나 오래되었어도 요청 중 TourAPI를 호출하는 폴백은 추가하지 않는다. 누락 데이터는 다음 수집 배치에서 처리한다.

## 동기화 처리 기준

1. 변경 목록의 `contentId`, 원본 수정 시각, 노출 상태를 DB와 비교한다.
2. 신규·수정되었거나 이전 상세 수집이 실패한 항목만 필요한 상세·이미지를 추가 수집한다. 동일한 원본 버전의 상세 수집이 완료된 항목은 재호출하지 않는다.
3. 삭제·비노출은 제공자가 반환한 상태에 따라 반영한다. 증분 목록에 없다는 이유만으로 삭제하지 않는다.
4. 기본 정보 저장과 상세 수집 완료 상태를 구분하여, 상세 수집 실패 항목이 다음 실행에서 누락되지 않게 한다.
5. 동기화 체크포인트와 재실행에 필요한 수집 상태는 DB에 영구 저장한다. 프로세스 내 `Map`만으로 중복 호출 방지를 보장하지 않는다.
6. 재시도를 포함한 모든 TourAPI 요청에 공통 속도 제한·일일 호출 한도를 적용한다. 여러 프로세스가 실행되어도 제한과 배치 중복 방지가 유지되어야 한다.
7. 날짜·지역·`showflag` 반복은 실제 API의 필터 동작을 검증한 뒤 축소한다. 변경 누락과 삭제·비노출 누락을 일으키는 파라미터 제거는 하지 않는다.

## 에이전트 확인 사항

- 작업 시작 시 이 문서를 읽고, TourAPI 관련 변경은 위 호출 경계에 맞게 설계한다.
- 구현·리뷰 시 `TourApiClient` 밖의 직접 HTTP 호출과 사용자 요청에서 발생하는 간접 TourAPI 호출을 모두 확인한다.
- 기존 코드의 정책 위반은 전환 대상이며 새로운 호출 경로의 선례로 삼지 않는다.
- 구현 완료 보고 시 정책 문서 작성과 실제 호출 구조 전환을 구분한다. 이 문서와 `AGENTS.md` 연결만으로 실행 시 호출이 자동 차단되지는 않는다.

## 실행 경계와 운영 설정

- `TourismModule` 내부의 수집 서비스만 TourAPI 포트를 주입받는다. 코스 수집 서비스도 이 모듈에 등록하고, 조회 모듈에는 raw TourAPI 포트를 export하지 않는다.
- 정기 관광지 수집(03:30 KST), 축제 수집(04:30 KST), 수집 CLI가 `TourApiPolicy.batch()` 문맥을 연다. 관광지·축제·코스 수집과 진단용 smoke CLI는 동일한 수집 경계·호출 예산을 공유한다. CLI 실행 시 다른 스케줄러는 비활성화한다.
- `TourApiClient`의 모든 실제 요청·재시도는 `TourApiPolicy.request()`를 거친다. 배치 문맥 밖에서는 HTTP 전송 전에 거절한다.
- PostgreSQL 세션 advisory lock으로 배치를 하나만 실행하고 실제 HTTP 요청 간격도 직렬화한다. 이 연결은 직접 PostgreSQL 연결 또는 세션 풀링을 사용해야 하며 트랜잭션 풀링 연결을 사용하지 않는다. 동일 서비스 키를 사용하는 실행 환경은 같은 DB와 한도 설정을 공유해야 한다. 이 DB를 거치지 않는 다른 시스템의 호출량까지 집계하지는 않는다.
- `TOUR_API_DAILY_LIMIT=1000`, `TOUR_API_MIN_INTERVAL_MS=1000`을 기본값으로 사용한다. 포털에서 승인된 실제 한도에 맞춰 조정한다. `tour_api_daily_usage`의 KST 날짜별 시도 수는 HTTP 전에 저장하므로 실패·재시도·재시작에도 유지된다.
- 목록 체크포인트(`TourismSyncRun.checkpointAt`)는 성공한 수집의 시작 시각이다. 해당 날짜를 포함해 다시 조회하여 당일 뒤늦은 변경을 놓치지 않는다. API 필터 동작을 추가로 검증하기 전까지 날짜·지역·노출 여부 필터는 유지한다.
- 장소와 축제의 `detailSourceModifiedAt`은 상세 수집이 완료된 원본 버전이다. 신규·변경·이전 실패 항목만 추가 수집하고, 실패 시 이전 상세를 유지한다. 주간 추천은 최신 목록 버전에 맞는 상세가 완료된 후보만 선정한다.
- 축제 상세 캐시가 없으면 기본 정보와 빈 상세 필드를 반환하며 요청 중 수집하지 않는다. 랭킹 미매칭·이미지 누락도 외부 검색으로 보충하지 않는다.

## 적용 순서

1. API 배포 전에 `pnpm --filter @haetteum/api db:deploy`로 `20260912160000_tourapi_db_only`를 포함한 마이그레이션을 적용한다.
2. 기존 기본 데이터가 있으면 `pnpm --filter @haetteum/api tourism:sync -- --mode=enrich-pending`으로 미완료 상세를 채운다. 초기 데이터가 없으면 `--mode=full`을 사용한다. full/incremental CLI와 정기 관광지 배치는 목록 수집 후 미완료 상세를 처리한다.
3. `pnpm --filter @haetteum/api festival:sync`로 축제 목록 및 미완료 상세를 수집한다. 코스 수집은 `pnpm --filter @haetteum/api course:sync`를 사용하며 원본 버전이 같으면 외부 상세 대신 누락된 DB 경유지 연결만 보완한다.
4. 호출 한도에 도달하면 중단하고 다음 KST 날짜에 같은 명령을 재실행한다. 완료된 상세 버전은 다시 호출하지 않는다. 개별 상세 실패는 재처리 대상으로 남기고 CLI 종료 코드/스케줄러 오류로 보고한다.
5. 상세 준비 후 랭킹 연결·이미지 backfill과 주간 추천 배치를 실행한다. 이 단계는 TourAPI 수집을 실행하지 않는다. 이미지 파일 다운로드·썸네일 변환은 별도 작업이다.

코드 변경 작업 중 운영/개발 DB에는 마이그레이션이나 실제 TourAPI 수집을 실행하지 않았다. 마이그레이션과 호출 제한은 별도 임시 PostgreSQL DB에서 검증한다.
